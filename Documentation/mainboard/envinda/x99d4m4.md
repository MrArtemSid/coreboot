# Envinda X99-D4M4

This board pairs an LGA2011-3 Haswell-EP/Broadwell-EP CPU (Grantley uncore,
PCI 1:15.5) with a client Lynx Point PCH.  The Huananzhi X99-QD4 uses the same
uncore path with a Q87 PCH and is kept as the regression control board.

## Status

Native coreboot source for the boot chain exists and builds.  No board has
been run with these images, so nothing below is a boot claim:

- The DRAM/uncore initializer is Intel's `UncoreInitPeim`, taken from the
  board's own stock firmware; it is executed from CBFS at the PE ImageBase
  recorded in the board contract.  Its size and SHA-256 are pinned per board.
- The QD4 module reads its MMCFG base through `PCD_PPI->Get64(1)` and gets
  0x80000000.  The D4M4 module never calls that getter: it carries the same
  value as its own .text datum at PE+0x106B8 and copies it at PE+0x2B484.
  Both values are checked before entry; a different base is refused.
- Each board serves its own factory `IntelSetup` variable (6090 bytes on the
  D4M4, 6091 bytes on the QD4).  The D4M4 payload is served verbatim: no field
  offset other than the ECAM datum has been proven on that image, so no ECC or
  DDR-frequency override is written.
- Production microcode (06-3f-02, 06-4f-01) is built in.  `06-4f-01` comes
  from `3rdparty/intel-microcode/intel-ucode-with-caveats/`: it is an Intel
  production image that upstream ships separately because it carries documented
  caveats, not an engineering-sample stepping.  ES steppings are not supported
  by this image.

Unresolved on hardware: D4M4 TOLM/TSEG programming and the timing of the
PEIM's `InstallPeiMemory` are unmeasured, and the QD4 evidence for them stays
scoped to the QD4 blob and policy.

## Building

```sh
cp configs/config.envinda_x99d4m4.native .config     # or config.huananzhi_x99_qd4.native
make olddefconfig
make
```

The board's `descriptor.bin`, `me.bin` and `uncore.bin` must be present under
`3rdparty/blobs/mainboard/envinda/x99d4m4/` (or `.../huananzhi/x99-series/`).
They are board-specific vendor data and are not part of the blobs submodule
history used by this tree.

`HAVE_IFD_BIN` selects coreboot's default "Unlock flash regions" policy, so the
build runs `ifdtool -u` on the image.  On these version-1 descriptors that
changes exactly two bytes of the pinned board descriptor: the GbE master
permission field `FLMSTR3` at 0x68 goes from `18 01 ff ff` to `18 01 08 08`
(read and write access for the GbE region only, requester ID 0x0118 kept; see
`util/ifdtool/ifdtool.c`, `unlock_descriptor()`).  Every flash region field and
the ME region are byte-identical to the board's descriptor/me input.  The ROM
descriptor is therefore not a byte-for-byte copy of the pinned file.

The in-image FIT header carries `C_V=1` and its checksum covers the table at
the header's size field (48 bytes for two microcode entries); the microcode
entries themselves carry `C_V=0` and no per-entry checksum, as
`util/cbfstool/fit.c:update_fit_checksum()` writes them.  The FIT entry
addresses equal the starts of the microcode entries in the CBFS microcode
blob.

## Tests

The C tests build and run with `make unit-tests`; the two real-PEIM cases need
the board blob and fail (not skip) without it:

```sh
GRANTLEY_UNCORE_BIN=3rdparty/blobs/mainboard/huananzhi/x99-series/uncore.bin \
    make unit-tests
```

The three Unicorn CPU tests need the `unicorn` Python module and an executed
bootblock image from a build of the same tree:

```sh
uv venv /tmp/grantley-tests
uv pip install --python /tmp/grantley-tests/bin/python unicorn
GRANTLEY_BOOTBLOCK_ELF=<obj>/cbfs/fallback/bootblock.elf \
    /tmp/grantley-tests/bin/python tests/cpu/intel/grantley-startup-test.py
```
